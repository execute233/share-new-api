# main integration and PostgreSQL upgrade checks

Integration target: `2fddb863f`, with first parent `6da7152f9`. The merge retains
main's features and wallet safeguards, plus the proxy pool, Shadowsocks and
per-target quality reports. It does not deploy or mutate a production database.

## Proxy API compatibility

- Channel create/update uses `proxy_id`. Omitting it on update preserves the
  binding; explicit `null` selects direct connections. Updating the channel and
  clearing its binding is atomic.
- Model preview also distinguishes omission from explicit `null`.
- Legacy `setting.proxy` and preview `proxy` values do not select an outbound
  connection. Runtime channel settings receive the proxy pool's resolved URL.
- Unbound, deleted or inactive proxies resolve to direct connections. Database
  and credential-decryption errors fail the operation. A proxy connection failure
  does not retry through a direct connection.
- HTTP, task submission/polling, management requests, artifact fetches and
  WebSocket handshakes use the resolved proxy. WebSocket connection reuse compares
  the resolved proxy, so changing the pool endpoint or credentials requires a
  reconnect.

## PostgreSQL preflight and rehearsal

Run `merge-main-postgres-preflight.sql` with the application's primary-database
connection and search path. It uses a read-only transaction. Adapt table names
only if the installation uses a custom GORM naming strategy. All four quota
columns must report `PASS`; `MISSING` is a schema mismatch, not a reason to bypass
the startup check.

No CodexDisguise channels were created in this installation. No type-62 data
conversion is included; main's type 62 is VLLM.

For a database requiring wider quota columns:

1. Back up the entire database with `pg_dump --format=custom`, and restore that
   backup into an isolated rehearsal database. Use a service file or existing
   credential mechanism rather than recording passwords in shell history.
2. Stop all writers to the rehearsal database. Capture the read-only preflight
   output and row-level exports of user quotas, orders, subscriptions, channels
   and proxy ciphertext into a secured local location.
3. In the rehearsal database, explicitly widen only quota columns that are still
   `integer`. An example for the default schema is below. Do not use it on
   production as part of this merge task.

   ```sql
   BEGIN;
   SET LOCAL lock_timeout = '5s';
   ALTER TABLE users
     ALTER COLUMN quota TYPE bigint,
     ALTER COLUMN used_quota TYPE bigint,
     ALTER COLUMN aff_quota TYPE bigint,
     ALTER COLUMN aff_history TYPE bigint;
   COMMIT;
   ```

4. Run the preflight again, start the integrated application against the isolated
   database, and let its normal migrations run. Do not set
   `SKIP_64BIT_QUOTA_SCHEMA_CHECK` as a workaround.
5. Compare quotas and existing rows against the captured data. Confirm login,
   redemption, order history, subscriptions and one request through each enabled
   proxy protocol. Verify existing encrypted credentials decrypt with the same
   `CRYPTO_SECRET` configuration; never print their plaintext.
6. Before a separately scheduled production upgrade, take a fresh backup and stop
   writers. If rollback is necessary, restore the backup together with the old
   application version; do not narrow populated BIGINT columns in place.

The proxy table is registered in main's unified migration path. Main no longer
contains a separate `migrateDBFast` path.
